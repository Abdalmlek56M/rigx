# RIGX — Practical Retail Core Mission (9 November 2026)

## Owner decisions applied (9 November 2026, second pass)

All decisions from `RIGX_OWNER_DECISIONS_FOR_DEEPSEEK_2026-11-09.md` are implemented:

1. **Partner net profit** = allocated revenue − discount − directly attributable expense − actual cost of all units. General overhead is not allocated. Snapshot is stored per physical unit, with the agreement effective on the order date and per-unit override support.
2. **Assembly allocation** is stored per component, defaults proportionally to standalone selling price, is admin-editable before publish, must total 100%, and is frozen into per-component order snapshots at sale.
3. **Reservation** remains atomic at `Confirmed` only.
4. **Completion** is a dedicated server-side action (`Sales.CompleteOrder`) from `Delivered`; payment is either confirmed `Paid` or explicitly `Waived` with actor/time/reason. `Waived` is never reported as `Paid`.
5. **Returns after payout** reverse the earning and create a recoverable negative balance that offsets future earnings before cash settlement. No historical payment is deleted.
6. **Returned units** enter `PendingInspection` and require a condition classification before returning to stock (or `Scrapped`).
7. **Media** has no automatic expiry; added a separate media backup/restore-verification script and policy.
8. **The 37,990 sample was corrected** (see Verification below).

## Completed

### 1. Transactional Retail Core module
Added `HardwareStore.Modules.Retail` as one bounded context for one-location stock, assemblies, orders and partner accruals, to keep receive/assemble/sell atomic without unsafe cross-module transactions. Catalog, Identity, Purchasing and Auditing remain separate.

Tables: `inventory_units`, `purchase_receipts`, `assemblies`, `assembly_units`, `store_orders`, `order_items`, `order_events`, `partner_agreements`, `partner_earnings`, `partner_settlements`.

### 2. Purchasing → real receipt
- `POST /api/v1/admin/retail/receipts/from-draft/{draftId}` converts a Draft purchase into individual Inventory Units with cost, condition, serial/warranty where supplied.
- Idempotent by unique `purchase_draft_id`; retries return the same units.
- Purchase Draft status extended to `Received`.
- No stock increase from Draft; only explicit receipt does.

### 3. Stock & Assemblies
- Individual unit identity, acquisition cost, condition, status (`Available/InAssembly/Sold`).
- Create assembly from available units atomically; unit cannot belong to two assemblies.
- Publish/unpublish, remove unit back to stock, swap between assemblies, disassemble.
- Complete-build sale consumes all component units once; assembly becomes Sold.

### 4. Orders / Sales
- Real server-side checkout replaces `RIGX-DEMO` local orders.
- Order reference generated by backend; cart clears only after confirmed creation.
- Public orders require account (existing policy).
- Admin order queue with status transitions (New→Confirmed→Preparing→Ready→Delivered→Completed/Cancelled) and manual payment verification. Paid is admin-confirmed only.
- Stock is claimed atomically on **Confirmed**; insufficient stock → 409 with no partial deduction.
- Cancel after confirmation releases units/assembly.
- Customer `/account/orders` history.
- Admin `/admin/orders`.

### 5. Partner accrual
- Versioned partner agreement (name, default %, active, effective dates).
- On **Completed**, earning snapshot = (line total − unit cost) × saved %, positive only.
- Settlement records allocate FIFO to outstanding earnings; history never deleted.
- Public APIs expose no cost/partner data.

### 6. UI
- `/admin/inventory/stock`: receive draft, list available units, create assembly, edit sale price, edit per-component allocation, publish/unpublish, disassemble; sold/disassembled assemblies no longer offer invalid actions.
- `/admin/orders`: order queue, status transitions, manual payment confirmation, explicit payment waiver with reason, server-gated completion, and return creation/inspection/rejection.
- `/admin/partners`: agreement (including loss-sharing flag), per-unit earnings, ledger with cash due/recoverable, settlement after offsets, and recoverable adjustments.
- Checkout now real; success shows backend reference/status. Cart/checkout copy no longer says “demo”.

### 8. Security check (this round)
- Anonymous `GET /api/v1/admin/retail/orders` → **401**.
- Anonymous `POST /api/v1/orders` (even with a CSRF token) → **401**; authenticated checkout requires the antiforgery token.
- Anonymous partner settlement and completion → **401**.
- Completion is a separate endpoint requiring `Sales.CompleteOrder`; the generic status endpoint rejects `Completed`. The migration grants the new permission only to roles that already have `Sales.ApproveOrder`.
- **Fixed leak:** the public assemblies payload previously included unit `acquisitionCost`, `serialNumber`, `status`, `assemblyId`, and receipt timestamps. It now returns only `productId/name/sku/condition`.
- Customer order listing is filtered by the authenticated `UserAccountId`.
