# مراجعة الأمن وحماية البيانات

## مصادر الحقيقة

ابدأ بهذه الوثائق قبل المراجعة: `docs/api/API_DESIGN_SECURITY.md`، و`docs/architecture/USERS_ROLES_PERMISSIONS.md`، و`docs/operations/DEPLOYMENT_OPERATIONS_BACKUP.md`، و`docs/testing/TESTING_STRATEGY.md`. راجع ERD أو متطلبات الميزة عند الحاجة لمعرفة مصادر البيانات والعلاقات. لو لم تحدد الوثائق أداة أو مدة أو حدًا أمنيًا، سجّل الفجوة ولا تخترع قيمة أو سياسة.

## خطوات المراجعة

1. **تحديد النطاق ومسار البيانات:** احصر نقاط الدخول، نوع المستخدم، البيانات الحساسة، مصادر البيانات والجهات التي تستقبلها. افصل الواجهات العامة عن الإدارية والداخلية.
2. **Authentication والجلسات:** ابدأ بآلية المصادقة الموثقة للنظام. في V1 يستخدم المشروع ASP.NET Core Cookie Authentication مع جلسات خادمية عبر `ITicketStore`؛ راجع حماية Ticket، وSession ID العشوائي الذي لا يُخزن إلا كـHash، والانتهاء الخامل/المطلق، والإلغاء والتزامن وخصائص `HttpOnly`, `SameSite`, `Secure` وCSRF وفق التصميم. لا تطبق مراجعة JWT أو Refresh Token إلا إذا دخلت آلية رموز فعلية ضمن نطاق معتمد لاحقًا؛ لا تفترضها أو تقترح استبدال Cookie بها.
3. **Authorization وRBAC:** طابق كل Endpoint حساس مع Permission من كتالوج الأدوار. تحقق من المستخدم النشط ودوره وصلاحيته في الخادم، ومن حدود صلاحيات الإدارة والتشغيل المصرح به. لا تستنتج صلاحية من اسم الدور أو من إخفاء زر في الواجهة.
4. **BOLA/IDOR وملكية السجل:** افحص استعلامات التفاصيل والتعديل والتنزيل بحيث تقيد السجل بهوية المستخدم/العميل الموثق، أو بصلاحية إدارية صريحة موثقة. اختبر معرفًا صحيحًا يخص مستخدمًا آخر وتحقق من عدم كشف وجوده أو محتواه.
5. **API Security والتحقق:** راجع إصدار المسار، الفصل بين Public/Internal DTOs، التحقق من كل المدخلات قبل منطق العمل، شكل `ProblemDetails`، عدم كشف التكلفة أو بيانات المورد في API العامة، ووجود Security Headers المحددة في وثائق API.
6. **SQL Injection:** افحص EF Core و`FromSql`/`ExecuteSql` وأي SQL يدوي. تحقق من استخدام parameters بدل تركيب النص من المدخلات؛ سجل أي مسار يجمع SQL والمدخلات كنقطة مراجعة أمنية. لا تعتبر تحقق الواجهة بديلًا عن parameterization.
7. **XSS وCSRF:** راجع ترميز المخرجات، حدود HTML المسموح، CSP، وخصائص Cookies. لأن تفاصيل CSRF وسياسة عرض النصوص غير مكتملة في الوثائق، تحقق من دفاع الخادم المناسب للآلية المستخدمة وسجل ما ينقص كفجوة تصميم؛ لا تفرض آلية أو استثناءات جديدة من دون اعتمادها.
8. **Idempotency وRate Limiting:** طابق العمليات الحساسة ومفتاح `Idempotency-Key` بنطاقه ومدة الاحتفاظ الموثقة، واختبر إعادة الطلب دون تكرار حجز أو خصم. قارن حدود Rate Limiting الفعلية بالقيم الموثقة في API Security، ولا توسعها أو تغيرها أثناء المراجعة.
9. **File Upload Security:** راجع امتداد الملف وMIME وMagic Bytes، إعادة معالجة الصورة على الخادم، تحويل WebP، إزالة EXIF، وحدود التخزين/العرض الموثقة. لا تثق باسم الملف أو MIME المرسل وحده، ولا تعلن فحص الملف إذا لم يُنفذ.
10. **Secrets Management:** ابحث في الشيفرة وملفات الإعداد والسجلات عن كلمات مرور وAPI Keys وTokens. تحقق من أن طريقة الحقن والتدوير والوصول موثقة وآمنة؛ إذا لم تحدد الوثائق مخزن الأسرار أو دورة تدويره، ارفعها كفجوة ولا تختَر خدمة أو إعدادًا نيابة عن المالك.
11. **Audit Logging:** راجع أن الإجراءات الحساسة والـ Allowlisted Actions تسجل المنفذ والتوقيت ومعايير التنفيذ والنتيجة، وأن السجل لا يسرّب كلمات مرور أو Tokens أو بيانات حساسة. تحقق من صلاحيات قراءة السجل وعدم تعديل السجل التاريخي وفق تصميم المشروع.
12. **Backup Security:** تحقق من شمول DB والوسائط، Checksum، إصدار المخطط، سجلات النسخ والاستعادة، نسخة ما قبل الاستعادة وDry-run المعزول. راجع التشفير والصلاحيات ومكان الاحتفاظ وفق السياسة المعتمدة؛ إذا كانت التفاصيل غير محددة فسجلها كقرار/فجوة ولا تفترض مدة RPO أو تخزينًا خارجيًا.
13. **Dependency Vulnerabilities:** راجع ملفات manifests وlockfiles ومخرجات فحص الاعتماديات عند توفرها. سجل الحزمة والإصدار والدليل والأثر، واتبع أداة ومعيار معالجة معتمدين؛ لا تثبت أداة أو تحدد SLA/عتبة شدة من تلقاء نفسك إذا لم توثقها السياسة.
14. **Security Testing:** اربط كل خطر باختبار مناسب من `TESTING_STRATEGY.md` أو أضف سيناريو مقترحًا عند غياب التغطية. افصل الاختبار المخطط عن الذي شُغل فعلًا، وسجل الأداة والمدخل والنتيجة. لا تدّعِ أن مراجعة الوثائق أو وجود هذه المهارة يثبت أمان التطبيق.

## التنفيذ المنضبط والتسليم

عند تطوير أو تعديل وظيفة حساسة، استخدم هذه المهارة مع `controlled-implementation`: حدّد النطاق والضوابط، لا تغيّر سياسات الأمن المعتمدة دون موافقة، ونفّذ أقل تعديل مصرح به، ثم سلّم الأدلة والاختبارات والفجوات. إذا تعارض مصدران أو غابت قاعدة مؤثرة، أوقف القرار الأمني المحدد وارفعه للمعماري/صاحب المشروع بدل التخمين.

## مراجعة التسجيل والتحقق من البريد

- راجع حالة Registration API منفصلة عن صفحات Next.js؛ لا تستنتج وجود واجهة أمامية من وجود Endpoint.
- طابق سلوك الحساب المعلق مع قرارات المالك في وثيقة API: لا جلسة ولا كلمة مرور قبل إثبات ملكية البريد، ولا تستنتج أن دور Customer يمنح صلاحيات قبل التأكيد.
- افحص إصدار الرمز وتخزينه وتسليمه عبر حدود الثقة، وتأكد أن الرمز أو رابط التأكيد لا يظهر في Audit أو Logs، وأن الاستهلاك لا يتم عبر GET.
- طابق حدود Rate Limiting الفعلية مع إعداد النسخة الواحدة ومراحل تفعيل المسارات، وسجل المسارات المؤجلة بدل وصفها كحماية منفذة.
- قبل فتح التسجيل في بيئة عامة، تحقق من اكتمال رحلة التأكيد والحماية التشغيلية والاختبارات وفق `docs/api/API_DESIGN_SECURITY.md` و`PROGRESS.md`; وجود Abstraction أو Fake Provider لا يثبت جاهزية الإرسال التجاري.
